# NetCrunch Telemetry Wire Format — v1

**Status:** Draft. Not yet frozen.
**Applies to:** NetCrunch 16 and later, Telemetry sensor.

This document is normative for client libraries in this repository. The key words MUST, MUST NOT,
SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119.

v1 deliberately specifies a **subset** of what the NetCrunch receiver accepts. The receiver is
tolerant of several additional shapes; they are listed in [Outside v1](#outside-v1) and MUST NOT be
emitted by a v1 client. Sending only the v1 subset is what makes a client forward-compatible.

---

## 1. Transport

A client sends UTF-8 JSON over HTTP `POST` with `Content-Type: application/json`.

Data arrives at a **Telemetry sensor**, which the operator creates in NetCrunch on the node that
represents the application. The sensor form displays the endpoint.

**Direct to a NetCrunch server**

```
POST https://<netcrunch-server>/api/rest/1/sensors/<sensor>@<nodeId>/update
```

**Through the NetCrunch Connection Cloud relay**

```
POST https://gw.netcrunch.io/tm/v1/<serverId>@<sensor>@<nodeId>/update
```

The relay form exists so that applications behind NAT, or without a route to the monitoring server,
can still report. Clients SHOULD accept a full endpoint URL as configuration rather than assembling
one from parts.

`<sensor>` is 3–20 characters from `[A-Za-z0-9-._]`.

### 1.1 Authentication

A client authenticates with a **bearer token** supplied by the Telemetry sensor:

```
Authorization: Bearer <token>
```

Clients MUST support configuring a token, MUST send this header whenever one is configured, and MUST
NOT place it in the URL, in a query parameter, or in the payload.

The token is scoped to **one sensor**. That bound is the point of the design: a token that leaked
from one application's configuration can write to that application's sensor and nothing else. A
server-wide token would make every leak a server-wide leak.

#### What the receiver does today

**The NetCrunch receiver does not yet verify this header.** Today the URL path segment *is* the
identity and the whole of the credential — `<sensor>@<nodeId>` for a per-node receiver, `<sensor>`
alone for a shared one, with the target node then selected by the payload. Anyone who can reach the
web server and knows those strings can write to that sensor.

The consequences are worth stating plainly, because they shape what a client library must do:

- **Treat the endpoint URL as a secret**, exactly as much as the token. Clients MUST keep it out of
  log output and MUST NOT include it in error messages or in exception chains — see the note on
  wrapping below.
- **Send the token anyway.** A client written now is forward-compatible with the receiver that
  enforces it, and a header the receiver ignores costs nothing.

Once the receiver requires a token, the URL stops being a credential and only the token needs
protecting. Until then, both do.

#### Wrapping is the trap

Every HTTP client in wide use puts the request URL into the errors it raises — `fetch`, `net/http`,
`HttpClient`, `urllib` and `Invoke-RestMethod` all do. A library that wraps such an error, or chains
it as a cause, publishes the credential into every log that formats the exception.

Clients MUST therefore construct their own failure from the status code alone, and MUST NOT attach
the original as an inner exception, `__cause__`, `__context__` or equivalent.

### 1.2 Update method

The final path segment names the update method. **A v1 client MUST use `/update` only.**

`/update` sets counters to the absolute values carried in the payload. Because a payload describes
current state rather than a delta, delivery is **idempotent**: a retried or duplicated POST cannot
corrupt the result. This property is the reason v1 excludes the incremental methods, and clients
SHOULD retry failed sends freely on the strength of it.

An unrecognised method segment is treated as `/update` by the receiver. Do not rely on this.

## 2. Envelope

```json
{
  "retain": 5,
  "remove": 1440,
  "counters": [],
  "statuses": {},
  "events": []
}
```

All members are OPTIONAL. A payload carrying none of `counters`, `statuses`, `events` or `data` is
valid but pointless; clients SHOULD skip the send instead.

| Member | Type | Meaning |
| --- | --- | --- |
| `retain` | number (minutes) | How long values stay live after this payload. Defaults to the sensor's configured retain time (5 minutes unless changed). |
| `remove` | number (minutes) | How long an object survives with no data before being removed entirely. Server default is 3600. |
| `counters` | array | See [§3](#3-counters). |
| `statuses` | object | See [§4](#4-statuses). |
| `events` | array | See [§5](#5-events). |
| `data` | object | See [§6](#6-data-objects). |

`retain` MUST be greater than the client's flush interval, or values will expire between sends. A
client SHOULD set `retain` to at least twice its flush interval.

`retain: -2` marks values as persistent — they are cached by the server and restored when the sensor
reloads. Reserve this for values that are genuinely meaningful across a restart.

## 3. Counters

A v1 client MUST emit the **detailed array form**.

```json
{
  "counters": [
    { "path": { "object": "SNMP",  "counter": "Requests Pending" },             "value": 42 },
    { "path": { "object": "Queue", "counter": "Depth", "instance": "inbound" }, "value": 5 }
  ]
}
```

| Field | Required | Notes |
| --- | --- | --- |
| `path.object` | yes | Groups related counters. |
| `path.counter` | yes | The measurement name. |
| `path.instance` | no | Distinguishes members of a set — a queue name, a partition, a worker id. |
| `value` | yes | Number. |

**Why not the shorthand map form.** The receiver also accepts `{"counters": {"Object/Counter": 5}}`,
splitting the instance at the **first** `.` in the string. Names that naturally contain dots — which
is most names — then split in surprising places. Encoding three fields into one string and re-parsing
it is a defect source with no upside, so v1 excludes it. Client APIs SHOULD take object, counter and
instance as separate arguments so the problem cannot arise.

### 3.1 Rates

The Telemetry sensor does **not** derive per-second values (`isPerSecSupported: false`). A counter
sent as a raw monotonic total will be charted as a rising line, not a rate.

Clients that want a rate MUST compute it, dividing the delta by the measured interval since the
previous snapshot — not by the nominal flush interval, which drifts. Emitting both the total and the
derived rate as separate counters is reasonable.

### 3.2 Lifecycle

A counter that stops appearing in payloads expires after `retain` minutes and is removed after
`remove` minutes. **No explicit deletion is required.** This is what makes short-lived, dynamically
named counters safe: when the thing being measured goes away, the client simply stops including it
and the server cleans up. Cardinality is bounded by object lifetime rather than by a retention policy.

## 4. Statuses

A status is a **state with an explanation**. Statuses are what NetCrunch alerting acts on; counters
are not. If something can be wrong, express it as a status.

```json
{
  "statuses": {
    "Importer": {
      "value": "Error",
      "message": "Batch 41 failed: connection reset",
      "critical": true,
      "data": { "batch": 41, "retries": 3 }
    },
    "Engine Phase": "running"
  }
}
```

| Field | Required | Notes |
| --- | --- | --- |
| `value` | yes | Non-empty string. The state itself. |
| `message` | no | Human-readable explanation. |
| `critical` | no | Boolean. Marks the status as critical. |
| `data` | no | Arbitrary JSON carried alongside for display. |
| `retain` | no | Per-status override of the envelope `retain`. |

A bare string is shorthand for `{ "value": "<string>" }`.

**Silent drops.** A status whose `value` is absent, empty, or not a string is discarded without
error. Client libraries SHOULD reject such statuses locally, at the call site, rather than letting
them vanish in transit.

**Key length.** Status keys are truncated to 500 characters by the receiver.

**Reserved keys.** Keys beginning with `@` are reserved — the receiver uses `@parser` and `@monitor`
internally. Clients MUST NOT emit a status key starting with `@`.

### 4.1 Timestamps

There is no timestamp value type. To report "when did this last happen", send **two** things:

- a counter carrying age in seconds — this is what an alert threshold can be set on
- a status whose `message` carries the absolute time — this is what a human reads

```json
{
  "counters": [ { "path": { "object": "Sync", "counter": "Last Success Age s" }, "value": 92 } ],
  "statuses": { "Last Sync": { "value": "OK", "message": "2026-08-10T09:14:22Z" } }
}
```

Clients MUST NOT send a raw monotonic clock or tick value. It is meaningless outside the process
that produced it.

## 5. Events

```json
{
  "events": [
    { "message": "Nightly import completed", "severity": "info" },
    { "message": "Batch 41 failed", "severity": "error" }
  ]
}
```

Each event MUST carry a non-empty string in `message` (or `body`). **Events failing this are
discarded silently by the receiver** — clients SHOULD validate at the call site.

Events are discrete occurrences. Do not use them for state; a condition that begins and later ends is
a status.

---

## 6. Data objects

A data object is a small structured view — a table or a chart — rendered on the sensor's page in
NetCrunch. It is how a script puts a process list or a throughput chart in front of someone without
anybody configuring a dashboard.

```json
{
  "data": {
    "processTable": {
      "type": "table",
      "name": "Process List",
      "columns": ["Name", "PID", "Memory"],
      "rows": [["node.exe", 1234, 45000], ["chrome.exe", 2345, 120000]]
    }
  }
}
```

The member is an object keyed by **id**. The id is the object's identity across payloads: re-sending
the same id replaces that object. Ids MUST be non-empty strings.

Three types are available to clients. A fourth, `internal`, is reserved for NetCrunch's own sensors
and MUST NOT be used.

| `type` | Required members | Shape |
| --- | --- | --- |
| `table` | `columns`, `rows` | `columns` is an array of headings; `rows` is an array of arrays. |
| `time-series` | `timestamps`, `values` | `timestamps` is epoch milliseconds. |
| `category` | `categories`, `values` | A labelled bar chart. |

Common optional members:

| Member | Applies to | Notes |
| --- | --- | --- |
| `name` | all | Display title. |
| `message` | all | A line of explanation shown with the object. |
| `status` | all | The object's own state — `"OK"`, `"Warning"`, `"Error"`. |
| `seriesName` | `time-series`, `category` | Label for the plotted series. |

**Parallel arrays must be the same length.** For `time-series`, `timestamps` and `values`; for
`category`, `categories` and `values`; for `table`, every row must have as many cells as there are
columns. The receiver does not check this and will render the mismatch, so clients MUST reject it.

**An unrecognised `type` is discarded.** The receiver logs a warning on the server and returns
success, so the client never learns. Clients MUST reject any type outside the three above.

Data objects expire on the same `retain` and `remove` clocks as everything else ([§2](#2-envelope)).

> **Not a substitute for a status.** A data object's `status` is part of what is displayed. Alerting
> acts on statuses ([§4](#4-statuses)). If a condition should raise an alert, send a status as well —
> a red table is not an alert.

## 7. Limits

| Limit | Value | Consequence of exceeding |
| --- | --- | --- |
| Pending payloads per sensor | 1000 | Further payloads are **dropped silently**, counted internally as `rejectedDueToQueueOverflow`. |
| Status key length | 500 chars | Truncated. |
| Data object array length | 1024 entries | **Truncated silently** — applies to `rows`, `columns`, `timestamps`, `values` and `categories` alike. Clients MUST reject rather than let entries vanish. |

The queue limit is per payload, not per value, so the mitigation is simple: **one payload per flush
interval, carrying every counter**. A client that sends one request per counter will hit the cap on
any real workload and lose data without being told.

## 8. Outside v1

The receiver accepts these. A v1 client MUST NOT emit them.

| Feature | Why excluded |
| --- | --- |
| `counters` shorthand map form | Ambiguous instance splitting — see [§3](#3-counters). |
| `counters[].metadata` | Accepted and then discarded server-side; the handler is a stub. Nothing reaches storage. |
| `histograms` | Parsed and attached to the result, but never surfaced. Incomplete. |
| `data` objects of type `internal` | Reserved for NetCrunch's own sensors. |
| `IncCounter` / `DecCounter` / `DeleteCounter` | Break idempotency — see [§1.2](#12-update-method). |
| XML and CSV native formats | Supported by the receiver for other ingestion paths. Out of scope for these libraries. |

---

## 9. Compatibility

Until v1 is frozen, anything here may change.

Once frozen, the format is a contract with software running inside other people's applications, on
their upgrade schedule, not yours. From that point:

- adding an OPTIONAL member is compatible
- adding a member the server requires is **not**
- narrowing what is accepted, renaming, or changing a type is **not**
- a client MUST tolerate unknown members in any response

The client half of authentication ([§1.1](#11-authentication)) is settled. What remains before
freezing is on the NetCrunch side: the receiver must issue tokens and verify the header. Until it
does, a client that sends one is correct and simply unenforced, so no client change is expected when
that lands.
